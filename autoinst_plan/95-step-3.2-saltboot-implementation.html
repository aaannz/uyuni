1. Verification results (2026-10-19)

Checked against the tree (583440e9b18) and saltboot-formula 1.1.0 on the agent VM (read-only). They refine the step 3.1 design:

  • More pillar keys are consumed than §1.1 listed. The execution engine (_states/saltboot.py, states/saltboot/init.sls) reads: partitioning, images, boot_images, terminal_kernel_parameters, saltboot:kernel_action (kexec|reboot|fail), saltboot:freeze_image, saltboot:force_redeploy, saltboot:force_repartition, saltboot:download_server (image URL mangling, _mangle_url), plus custom_info:saltboot_*. pillar.get('saltboot') is not None is also used as a “managed by the saltboot formula” switch (skips the bundle-sync check), so the generator always emits a saltboot dict for a resolved terminal.
  • The saltboot formula form (form.yml) carries three values the design did not model: top-level terminal_kernel_parameters, and under saltboot: kernel_action and freeze_image. A lossless migration needs them → suseSaltbootConfig gains terminal_kernel_parameters VARCHAR and freeze_image BOOLEAN, both nullable (null = inherit, same rule as kernel_action). Additive refinement of §2.2, no new decision.
  • Partition enums from the form: format ∈ {btrfs, ext4, xfs, vfat, swap} (blank allowed), flags ∈ {swap, raid, bios_grub, esp, boot} (blank allowed), disklabel ∈ {gpt, msdos, none}, type ∈ {DISK, RAID}, RAID level 1 only. Disk keys: type device level devices disklabel partitions and, for disklabel: none, the partition fields directly on the disk.
  • SaltbootUtils.deleteSaltbootDistro §1.9 bug confirmed in code: the nameV profile is re-pointed with makeCobblerFilterName instead of makeCobblerFilterNameV.
  • RegisterMinionEventMessageAction#prepareRetailMinionForSaltboot already calls the full MinionPillarManager.generatePillar(minion) after the group assignment, so a generator in the full path covers registration.
  • XML-RPC (redstone) has no nil, so tombstones (JSON null) cannot cross the XML-RPC boundary: the API maps the string $delete to/from null. Hibernate JSONB keeps real nulls.

2. Decisions taken in this step

# Decision Reason
S1 While a saltboot formula applies, SaltbootUtils keeps reading the formula pillar; the domain is read when no formula pillar exists. Dual-write keeps both equal, but download_server (free text) vs proxy FK (may be unresolved) differ — formula-first preserves today’s MASTER= exactly. Domain takes over on formula unassignment, as §4.2 intends.
S2 Permissions: config CRUD/list/get/assignments → Org Admin (partitioning may carry luks_pass); branch ops, terminal ops → permission on the target group/system (FormulaUtil checks, as formulas today). Closest to the formula permission model; configs are org-wide objects.
S3 API edits of a branch/config/assignment/terminal flag whose target still has a saltboot formula are refused with an explanatory fault (§4.2). Avoids silent no-ops: the domain generator is suppressed while a formula applies.
S4 saltboot pillar category is stored as a minion pillar row written by SaltbootPillarGenerator (like the other generators) and added to the full path of MinionPillarManager. suma_minion.py merges non-formula categories recursively; no Python change.
S5 resetSaltbootRedeployFlags additionally clears the domain flags and regenerates the saltboot pillar. Flags moved to SaltbootTerminal; otherwise they would stay set forever.
