Step 1.8 Addendum — Web UI install-type guard (distro create/edit NPE fix)

1. Finding (user report, 2026-10-15)

Creating a distro via the web UI crashed with:

java.lang.NullPointerException: Cannot invoke
"com.redhat.rhn.domain.kickstart.KickstartInstallType.isSUSE()" because
"this.installType" is null
    at KickstartableTree.getDefaultInitrdPaths(KickstartableTree.java:394)
    at KickstartableTree.getInitrdPath(KickstartableTree.java:439)
    at BaseTreeEditOperation.validateBasePath(BaseTreeEditOperation.java:168)
    at BaseTreeEditOperation.store(BaseTreeEditOperation.java:81)
    at TreeCreateOperation.store(TreeCreateOperation.java:63)
    at BaseEditAction.execute(BaseEditAction.java:65)

2. Root cause

  1. BaseTreeAction#processCommandSetters assigned KickstartFactory.lookupKickstartInstallTypeByLabel(form value) to the tree without a null check. A posted installtype label that is not in rhnKsInstallType (unknown label, stale page, empty install-type list — e.g. branch code deployed before the branch DB deltas) silently produced a tree without an install type.
  2. BaseTreeEditOperation#validateBasePath → KickstartableTree .getInitrdPath() → getDefaultInitrdPaths() dereferences installType.isSUSE() (same landmine in getDefaultKernelPaths and the two xen getters). Even without the NPE, applyDistroKernelOptions() (step 1.2) would throw KernelOptionsBuilderException one line later — the factory routes unknown/null install types.
  3. Pre-existing legacy behavior: phase 1 never touched KickstartableTree, BaseTreeAction or BaseEditAction (verified via git log — only the maven/jakarta/infrastructure commits touch them). The XML-RPC path was already guarded (KickstartTreeHandler#getInstallType throws NoSuchKickstartInstallTypeException); only the Struts path was not.

Trace-forensics note: the stack trace line numbers (TreeCreateOperation .java:63 = branch’s super.store(); stock 5.3.1 has it at line 70, verified via javap line tables) proved the report came from a branch deployment — on the VM the running jar was stock after the step-1.7 rollback while the DB retained opensuse16.1 (id 13).

3. Fix (minimal, action-level only — user-locked scope)

BaseTreeAction#processCommandSetters: resolve the label defensively and return a ValidatorError instead of setting a null install type (covers create and edit; mirrors the XML-RPC guard):

  • null/unknown label → new ValidatorError("kickstart.tree.invalidinstalltype", installTypeLabel) — the UI shows the offending label.
  • The null-label check sits before the lookup because HibernateFactory#lookupObjectByParam throws a raw NPE on a null parameter (Objects.requireNonNull).
  • New message key kickstart.tree.invalidinstalltype (“The installer type is not valid: {0}”) in StringResource_en_US.xml and StringResource_de.xml (repo convention; other locales follow l10n sync).
  • No domain hardening (deliberate — user decision): a null install type on a tree remains a programming error; the action guard prevents the only realistic source.

4. Tests

  • New DB-backed BaseTreeActionTest (java/core/src/test/java/com/redhat/rhn/frontend/action/kickstart/tree/, JMockBaseTestCaseWithUser + ByteBuddyClassImposteriser for DynaActionForm/HttpServletRequest — first Struts-action-level test in the tree, following the step-1.1 jMock pattern):
  • unknown label → ValidatorError key kickstart.tree.invalidinstalltype, install type stays null, no NPE;
  • missing (null) form value → same rejection;
  • valid label (opensuse16.1) → type set, label/basepath applied, store values untouched.
  • VM run (pgsql-4eclipse container, branch schema): 16 tests green — 3 BaseTreeActionTest + 8 TreeCreateOperationTest + 5 TreeEditOperationTest.
  • Local sandbox: mvn -f java/core compile / test-compile / checkstyle:checkstyle clean.
