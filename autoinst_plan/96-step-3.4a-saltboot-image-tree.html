Step 3.4a — Saltboot Distro as Image-Based Tree

Design for roadmap step 3.4a (10-roadmap.md Phase 3): every saltboot boot image gets a Java-side distro record — a KickstartableTree backed by an ImageInfo instead of a channel — with a dedicated saltboot install type. Prerequisite for step 3.4b (saltboot builder routed by install type, 97-step-3.4b-saltboot-kernel-options.md) and a building block for the Cobbler exit (G6: Java-side record of kernel/initrd per bootable distro).

1.3 Install type

KickstartInstallType.getCobblerBreed() returns redhat for any label that is neither generic_rpm nor SUSE; getCobblerOsVersion() falls back to virtio26 for non-redhat/suse breeds. isGeneric() = label starts with generic (so generic_rpm routes to the RHEL builder and cannot be reused). isRhel6OrGreater()/isRhel7OrGreater() are true for any unknown label (only reachable from kickstart paths).

1.4 Image side

  • Saltboot distros are created when a Kiwi pxe image with a boot image and no bundles is inspected (ImageInspectAction:286-289 → SaltbootUtils.createSaltbootDistro(imageInfo)) and by the cobbler migration task (SaltbootMigrationUtils.migrateSaltboot → createSaltbootDistro(imageInfo, distros, con)).
  • Kernel/initrd are ImageFile rows (type = kernel / initrd), path = OSImageStoreUtils.getOSImageStorePathForImage(image) + ImageFile.file; arch = ImageInfo.getImageArch().
  • Deletion: ImageInfoFactory.delete → SaltbootUtils.deleteSaltbootDistro → removes files → removes the ImageInfo.

3.3 Lifecycle

Two kinds of image trees, no flag column: the generated tree of an image is the one whose label equals the image’s generated label (name-version-revision); every other image tree is user-created.

  • Generated — create: SaltbootUtils.createSaltbootDistro(imageInfo, distros, con) first ensures the generated tree (before its early return for an existing distro), so both callers — inspect and the cobbler migration — create it: label = name-version-revision, org = image org, install_type = saltboot, kstree_type = externally-managed, base_path = parent dir of the kernel/initrd paths (T3; error if they differ), image = imageInfo. Missing kernel/initrd → existing SaltbootException, no tree. If the label is taken by another tree (§6), is longer than 64 characters or does not match the image-tree label rule ^[-_.0-9A-Za-z]{1,64}$ (O1/O2, §5a.2), the tree is skipped with a warning — the cobbler distro is still created as today. The same rule validates user-created image tree labels (§3.4).
  • Generated — delete: only together with its image. The new delete call refuses it (it mirrors the cobbler distro, which lives as long as the image).
  • User-created: created/updated/deleted through the new API (§3.4) — pure data in this step (T6: no cobbler object; consumers arrive with 3.4b / the trigger model 3.5 / G6). Optional kernel_options(_post) are stored as typed.
  • Image deletion: ImageInfoFactory.delete removes all trees of the image explicitly (keeps the Hibernate session consistent) before removing the ImageInfo; the FK cascade is the safety net. Image trees are never referenced by kickstart profiles/sessions (the filtered lookups never hand them out), so no rhnKickstartDefaults FK blocks the delete.
  • Migration of existing images: new UpgradeCommand task upgrade_satellite_create_saltboot_trees queued idempotently from upgrade/next; it ensures the generated tree for every Kiwi image that has both kernel and initrd files and no bundle file (the inspect condition). No cobbler access needed (T6) → runs synchronously in upgrade(), like MIGRATE_SALTBOOT_DOMAIN.

5a.2 Open items — decided (user, 2026-10-19): O1 (a), O2 (a)

Label column stays VARCHAR(64) for now; a generated label longer than 64 skips the generated tree with a warning. Image trees use their own label rule ^[-_.0-9A-Za-z]{1,64}$ (dots allowed); the generated label is the exact name-version-revision. Both are implemented in 3.4a-2 (image-tree create path); 3.4a-1 is unaffected.

  • O1 — label length. Generated labels name-version-revision can exceed VARCHAR(64). Options: (a) keep 64, skip the generated tree with a warning when too long (typical POS_Image_JeOS7-7.1.0-3 is ~25 chars); (b) widen label to 256 in this session’s script (also matches the 255 in the regex; check ISS export/import and UI field lengths). Recommendation: (a), as long as no real-world image names exceed it.
  • O2 — dots in labels. Image versions contain dots, the kickstart label rule forbids them. Options: (a) image trees get their own rule ^[-_.0-9A-Za-z]{1,64}$ (no DB constraint exists; image trees are never served under /ks/dist/<label>), generated label = exact name-version-revision; (b) sanitize dots to _ in the generated label and keep one rule. Recommendation: (a) — the label stays the recognizable image identity and matches the saltboot cobbler names. Affects 3.4a-2 code only (the rule lives with the image-tree create path), decided now.

6. Risks

  • Unknown leak sites — any future HQL over KickstartableTree that does not go through the filtered factory methods sees image trees; mitigated by the review list in §1.2 and a test per filtered lookup; reconsider a Hibernate-level split (@SQLRestriction) if leaks accumulate.
  • Shared label space — a later reposync of a custom (org-owned) tree whose label equals an image tree label fails on the unique index (vendor trees have org_id NULL and never collide). Image labels (name-version-revision) and distro labels rarely overlap; accepted, and the generated-tree path skips instead of failing (§3.3).
  • blend dependency order — rhnKickstartableTree → suseImageInfo; check tables.deps for cycles before relying on it.
